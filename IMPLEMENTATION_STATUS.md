# Retail POS implementation status

Source audit updated 23 November 2026. The latest verified checkpoint is 617 tests. BUILD_STATUS.md records current native evidence. Historical details below retain wider outstanding scope.

This document compares the **entire** [feature specification](FEATURE_SPECIFICATION.md) with the source currently present. It is not a claim that the desktop application, long-term specification, or multi-tenant SaaS is complete.

The current product is a local Kotlin/Compose desktop foundation. Tenant-scoped shop records, owner/staff password access, cash/credit sales, buying/selling packs, stock receiving/counts/history, cash shifts, linked cash returns, reports/CSV, receipt output and encrypted manual backup/recovery exist. The current integrated run passes **555 tests** (77 shared + 478 desktop), zero failures, errors or skips, including basket discounts, supplier profiles, count sessions, labels, branded receipts, statement PDFs, purchase orders/partial deliveries and classified stock removals. The Linux distributable builds with JDK 17 and installed Gradle 8.13 in offline dependency mode. Earlier test counts are historical checkpoints. Selected disconnected native checks and PDF renders are recorded in BUILD_STATUS.md; merchant and hardware acceptance remain pending.

The current batch integrates fractional receive/sell/count/cash-return journeys, exact persisted quantities and historical precision/conversion snapshots, draft recovery, optional CSV quantity precision and encrypted backups. Per-product precision is immutable after creation (0–6 decimal places). Stock is held as Long scaled units capped at 9,007,199,254,740,991 with exact projection checks; individual transaction quantities are limited to Int.MAX_VALUE scaled units. Legacy precision-zero balances with a fractional remainder stay visible without silently changing their unit/precision; only the whole portion is sellable until explicitly reconciled.

Percentage item discounts, SKU/category/brand/alias/favourite metadata and filters, dated customer statements and dated receipt-name supplier statements have integrated automated coverage. New bounded slices add atomic opening/closing denomination sheets, local six-digit staff PINs and searchable offline help launching practice in a separate isolated sample process. None of these additions establishes full supplier accounting, secure blind cash accountability, encrypted working storage or online services.

The coordinating agent inspected actual desktop sample workflows inside a Linux network namespace with no external routes: an unapplied fractional edit blocked payment, keyboard Tab/Return applied it, 1.375 kg with 12.5% discount totalled ₦1,203.13 and ₦2,000 tender produced ₦796.87 change. A separate undiscounted sale followed by a 0.375 kg cash return/restock left 9 kg. See artifacts/desktop-fractional-*.png and BUILD_STATUS.md for exact evidence. An actual denomination close saved 9 × ₦1,000 against ₦10,000 expected and retained its ₦1,000 shortage/count sheet in Past shifts. Offline Help rendered; the rebuilt installed binary passed direct practice-launch readiness, duplicate suppression and child termination checks, and an isolated cashier subsequently opened practice through the actual Help button. The coordinating agent also configured a PIN with the full staff password and unlocked the sample cashier with it; restricted tools stayed unavailable. Full PIN/device security and broader UI acceptance remain separate. These are targeted checks; comprehensive keyboard/failure journeys, other new UI paths, Windows/peripherals and merchant acceptance remain separate.

The completed first wave adds reasoned whole-basket discounts with exact stable line allocations and cash-return conservation; stable supplier profiles/contact terms/history and explicitly linked account statements; durable multi-item count drafts with movement-aware stale checks and atomic posting; current-product/selling-pack Code128 labels with PNG export/native print submission; and versioned shop/contact/footer settings with captured identities for new receipts. Branded receipts support offline A4/58/80 mm PDF output. Dated customer and stable-ID supplier account PDF statements reuse reconciled histories, preserve exact kobo amounts, label current contacts separately from historical receipt names, and repeat statement identity/period on continuation pages. Automated output checks do not verify native file dialogs, paper delivery, every keyboard path or merchant usability. Broader templates, tax invoices, sharing and server delivery remain pending.

New-product CSV import remains atomic and add-only. A separate reviewed update importer now supports existing catalogue records with stale checks and atomic history. Rendered desktop/isolated-offline checks and their limits are recorded in BUILD_STATUS.md; physical peripherals, Windows packaging and merchant studies remain outstanding. No whole functional specification section is complete.

## Important distinctions

### Local tenant separation is not a finished multi-user SaaS

Business queries/mutations carry a tenant ID and composite relationships. The UI owner password gate chooses which local workspace to enter. Local staff sessions enforce role permissions in the running application. That does not establish authenticated server-side tenant memberships or isolation from someone who can read/edit the workstation's SQLite files.

The working database is not encrypted. The repository is a local adapter, not a network authorization service. Local staff credentials live separately from business backups. No online identity provider, Heroku backend, deployment, sync transport, or remote staff access was identified. The app must not be advertised as a production multi-user online service yet.

### An outbox is not synchronization or backup

Pending changes are recorded locally. No transport acknowledges them remotely. The online status must remain explicitly disconnected; a queue count or internet connection does not prove a remote copy exists.

Encrypted backup files can be saved manually or by the opt-in running-app session scheduler, with versioned local retention. It covers the selected tenant's saved business records; it excludes owner credentials, unfinished basket files and device settings. Restore creates another tenant rather than overwriting an existing shop. Automated tests cover tampering, wrong passwords, malformed input, tenant boundaries, ledger/debt consistency and repeated restore. Recovery on independent machines and broader security review remain outstanding.

### New output has narrow semantics

- OS print submission does not prove paper delivery or support for a particular thermal printer. Windows/system-dialog and real hardware verification remain required.
- Text and PDF receipts are local saved-sale copies; neither is a tax invoice or bank-payment verification. PDF statements are dated account summaries, not sales receipts. Sharing/server document delivery remains unavailable.
- CSV exports are local, selected-tenant datasets. Current product/customer snapshots are explicitly distinct from date-filtered historical transactions.
- Supplier balances/payments retain original received-stock records and historical supplier-name strings. Stable supplier profiles group only explicitly linked receipts into reconciled dated accounts. This does not implement supplier credit notes, account adjustments or full accounting.
- Returns currently cover original cash-sale items and cash refunds, with an optional sellable restock flag. They do not cover the full exchange, credit-return, payment-provider, quarantine, or approval scope.
- Reports deliberately do not calculate profit because historical COGS is incomplete. Do not present sales minus stock purchases as profit.

### Shared code is prepared, not shipped on every platform

Domain/UI sources live under commonMain, but only a JVM target is currently configured. Android/iOS builds, platform persistence, secure storage, printing, and hardware adapters remain future implementation. SQLite JDBC is desktop-specific; using common source folders does not make it a Room Multiplatform implementation.
